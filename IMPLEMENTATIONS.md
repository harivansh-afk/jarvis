# Existing implementations for talking to ongoing coding work

Research snapshot: 2026-09-10. Scope: a voice presence that can discuss and control several **already-running** coding sessions on Linux Spark, using a terminal/process interface such as Mux/muxd rather than replacing the coding harness.

**The closest engineering combination is ccmux's observation of existing processes plus Happier's cross-session voice control model.** HAPI supplies a smaller, concrete example of a realtime voice agent relaying work to a separate coding agent. None of the inspected systems establishes an off-the-shelf GPT-Live → Astra → existing Mux/muxd solution. That is an architectural assessment, not a claim that the entire ecosystem was exhaustively searched.

## Shortlist and evidence level

| Project | What is useful here | Existing live session boundary | Evidence in this review |
|---|---|---|---|
| [ccmux](https://github.com/epilande/ccmux) | Process discovery, terminal/session binding, transcript reading, events, targeted input | Discovers agents already in tmux; no launcher required. Mux needs a different terminal adapter. | Source inspected; 64 focused tests run successfully |
| [Happier](https://github.com/happier-dev/happier) | One voice assistant with explicit targets and a set of tracked sessions; remote/mobile clients | Can follow external transcripts. Codex takeover spawns a resumed managed runtime; this is not attachment to an arbitrary live PID. | Source and relevant tests inspected; not run |
| [HAPI](https://github.com/tiann/hapi) | Separate realtime voice frontend, coding-agent messages, permission forwarding, context updates | Wrapper/runner architecture. Voice tools target one current session. | Source and relevant tests inspected; not run |
| [VoiceMode](https://github.com/mbailey/voicemode) | Local speech, audio interruption and coordination between speaking agents | MCP tool used by participating agents; does not by itself discover/control five external coding sessions | Source inspected; not run |
| [Agent Deck](https://github.com/asheshgoplani/agent-deck) | Persistent supervisor, delivery verification, handling human drafts and approval overlays | Primarily its own registered tmux sessions; not a generic Mux observer | Selected source inspected; not run |

These rankings concern fit and inspectable lifecycle behavior, not stars, author fame, or a blanket code-quality endorsement.

## 1. ccmux: the strongest precedent for the machine interface

At [`ab2c51a`](https://github.com/epilande/ccmux/tree/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b), discovery obtains processes with `ps` and reads Linux working directories from `/proc/<pid>/cwd`. Binding joins process TTYs to tmux panes, then uses ancestry for PTY-allocating wrappers. Native session matching is separate: hooks, transcript evidence and a bounded assignment algorithm associate conversation identity with the process/pane. This directly addresses the difficult case of several agents sharing a project directory. [Process discovery](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/processes.ts), [TTY/ancestry binding](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/binder/primitives.ts), [assignment](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/binder/assign.ts).

Session references distinguish exact IDs/panes from fuzzy names and refuse ambiguity. Status combines hooks, logs and terminal patterns; these have different confidence and freshness. The daemon exposes HTTP/SSE for state changes and transcript/input operations. Thus Astra could consume machine facts without becoming the execution harness. The local daemon binds to loopback by default; it is not itself a mobile voice service. [Session reference resolution](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/session-ref.ts), [architecture](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/docs/architecture.md), [server](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/server.ts), [configuration](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/lib/config.ts).

Input uses stable pane IDs and literal keys or named tmux buffers with bracketed paste. This reaches the existing TUI without restarting it. **But terminal input still shares the human's composer.** A concrete source caveat: `handleSendToSession` sanitizes control characters and targets a stable pane, but does not invoke the foreground-liveness/ambiguous-wait guards used in the handoff path. A stale target could therefore be more dangerous through raw `send` than through guarded handoff. Do not assume a tool named “send” already has safe transaction semantics. [Input implementation](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/pane-io.ts), [raw send and handoff handlers](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/server.ts), [delivery guards](https://github.com/epilande/ccmux/blob/ab2c51aac23e56b3bdb1a8b5ff9fc6816db3905b/src/daemon/send-guards.ts).

**Validation performed:** after a frozen dependency install with lifecycle scripts disabled, ran the session-reference, binding-primitives, assignment, send-guards and pane-I/O suites: **64 passed, 0 failed, 892 assertions**. These exercise identity ambiguity and input construction with test doubles. They do not establish live Codex interaction, audio latency, or compatibility with Mux/muxd. The inspected revision is release v1.4.1, committed September 10; recent development is evidence of activity, not proof of runtime reliability.

## 2. Happier: the closest product model for “talk to all my work”

At [`1535ac3`](https://github.com/happier-dev/happier/tree/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8), the voice implementation separates a primary action target from the sessions being tracked. Targets can be resolved by title; tool resolution supports an explicit session ID, current session, or global primary/last-focused target. This is a better starting point for five sessions than letting whichever window happens to have focus silently determine every command. The action protocol includes session listing, messages and permission responses. [Target management](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/apps/ui/sources/voice/tools/actionImpl/sessionTargets.ts), [tool target resolution](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/apps/ui/sources/voice/tools/resolveToolSessionId.ts), [action executor](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/packages/protocol/src/actions/actionExecutor.ts).

The crucial limitation is visible in code: direct Codex sessions can be browsed/followed, but **takeover calls `spawnSession` with `resume: linked.remoteSessionId`**. A conflicting trusted Happier owner requires `forceStop` and is stopped before spawning. That preserves conversation continuity while changing runtime ownership; it does not prove noninterfering control of Hari's current Codex processes. Unknown external owners are not magically converted into controllable processes by transcript access. [Takeover RPC](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/apps/cli/src/api/machine/rpcHandlers.directSessions.ts), [Codex follow/resume adapter](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/apps/cli/src/backends/codex/directSessions/providerOps.ts).

Engineering evidence includes explicit owner matching, source/home affinity validation, tests rejecting ambiguous or escaping Codex homes, and a dedicated Codex takeover/persist/continue E2E suite. Those tests were inspected, not executed here. The project advertises self-hosted encrypted web/mobile/desktop clients and several voice backends, including a daemon-backed reasoning agent. That makes it a serious product precedent, but its encryption and provider boundaries were not audited in this review. [Takeover tests](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/apps/cli/src/api/directSessions/takeover/resolveDirectTakeoverSpawnOptions.test.ts), [E2E test](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/packages/tests/suites/core-e2e/directSessions.codex.appServer.takeoverPersistContinue.feat.sessions.direct.slow.e2e.test.ts), [product/backend claims](https://github.com/happier-dev/happier/blob/1535ac398a6d28b00fb2d9be7394d6a0cb24b7f8/README.md).

## 3. HAPI: a useful compact voice-to-coding bridge

At [`10042f7`](https://github.com/tiann/hapi/tree/10042f79c699f7d340dc838192a8611e0e8df08c), HAPI has a real two-agent boundary: a voice assistant forwards requests to a coding agent, then receives context updates. Its documented voice providers are ElevenLabs, Gemini Live and Qwen Realtime; GPT Live would require a provider integration. Voice history starts with a small recent-message bootstrap and streams older context afterward. This is useful for keeping connection startup independent of a long coding transcript. [Voice architecture](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/docs/guide/voice-assistant.md), [context planning source](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/web/src/realtime/hooks/voiceContextPlan.ts), [context tests](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/web/src/realtime/hooks/voiceContextPlan.test.ts).

The source also exposes the scaling limit: `messageCodingAgent` resolves the current realtime session; the permission tool accepts only allow/deny and selects the **first** pending request. Neither tool accepts an explicit session/request identity. That is inadequate as-is for conversational approval across five independent jobs. HAPI's runner/wrapper and Codex local-TUI/remote-app-server design should not be mistaken for passive attachment to arbitrary existing terminal processes. [Voice tools](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/web/src/realtime/realtimeClientTools.ts), [agent integration modes](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/docs/guide/agents.md).

Its hub is self-hosted, with optional external push and voice providers. The documented permission/completion notifications provide useful event vocabulary for proactive speech; this review did not test how promptly or appropriately it actually speaks. [Privacy boundaries](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/docs/privacy.md), [notifications](https://github.com/tiann/hapi/blob/10042f79c699f7d340dc838192a8611e0e8df08c/docs/guide/notifications.md).

## 4–5. Components worth studying, rather than adopting as the whole system

**VoiceMode** at [`5c1b3e4`](https://github.com/mbailey/voicemode/tree/5c1b3e4d9421cd365d039da1d29827a0a83a18c7) implements speech as an MCP capability, with optional local Whisper/Kokoro services. Its “conch” records speaker/session/project identity, uses a kernel file lock during active conversation, and a PID/expiry-checked reservation between turns. There are focused queue, deadlock and playback-interruption tests. That is a useful precedent for audio ownership and crash recovery, but a model blocked in unrelated work still needs a separate responsive voice controller. It is not an existing-session registry or a full-duplex Live frontend by itself. [Overview](https://github.com/mbailey/voicemode/blob/5c1b3e4d9421cd365d039da1d29827a0a83a18c7/README.md), [conch source](https://github.com/mbailey/voicemode/blob/5c1b3e4d9421cd365d039da1d29827a0a83a18c7/voice_mode/conch.py), [interruption tests](https://github.com/mbailey/voicemode/blob/5c1b3e4d9421cd365d039da1d29827a0a83a18c7/tests/test_playback_interrupt.py).

**Agent Deck** at [`61cc4d6`](https://github.com/asheshgoplani/agent-deck/tree/61cc4d688e34ca40225bb71635e42e6e44d5bbb4) has a persistent conductor that supervises registered tmux sessions, with optional remote channels and heartbeat. Its strongest relevant detail is input lifecycle: Codex approval handling re-reads and fingerprints the visible prompt before sending a numbered key, then verifies the outcome. Composer guards also notice human drafts. However, the guard explicitly allows proceeding after failed draft clearing, accepting residual merge risk; that policy is unsuitable for a strict noninterference requirement. Study these race conditions, not only the happy-path API. [Conductor](https://github.com/asheshgoplani/agent-deck/blob/61cc4d688e34ca40225bb71635e42e6e44d5bbb4/docs/conductor/README.md), [Codex approval source](https://github.com/asheshgoplani/agent-deck/blob/61cc4d688e34ca40225bb71635e42e6e44d5bbb4/internal/send/codex_approval.go), [composer guard](https://github.com/asheshgoplani/agent-deck/blob/61cc4d688e34ca40225bb71635e42e6e44d5bbb4/internal/send/guard.go).

## Codeberg and other candidates

Codeberg was explicitly searched through its public repository API because browser search was robots-blocked. Queries included `jarvis`, `codex`, `tmux` (name order and most recently updated), `voice`, and `voice assistant`. These were bounded result pages, not an exhaustive forge inventory. The most directly branded candidate, [Admethius/jarvis-smart-agent](https://codeberg.org/Admethius/jarvis-smart-agent), was cloned and inspected at `1935ea5b42036574541f7a0ad5e679d05fe8671c`. It is an OpenCode meta-agent plus a Python MCP server for project manifests, memory, todos and Git. Its session handoff is persisted context, not live PTY/agent-process control; no qualifying voice-to-existing-Codex implementation was established. Other results included voice assistants, tmux utilities and continuity stores, but none earned a place in this shortlist. This means **no qualified Codeberg result found in this search**, not that none exists. [Pinned architecture](https://codeberg.org/Admethius/jarvis-smart-agent/src/commit/1935ea5b42036574541f7a0ad5e679d05fe8671c/docs/architecture.md).

[cmux](https://github.com/manaflow-ai/cmux) is a relevant programmable terminal/notification precedent, but its primary product is a macOS terminal, so it is less directly applicable to the Linux daemon interface. [OpenClaw's ACP resume documentation](https://docs.openclaw.ai/tools/acp-agents/delivery) explicitly restores upstream history through `session/load` into a newly created OpenClaw session; it does not establish attachment to an arbitrary running terminal agent. [Goose's client/server discussion](https://github.com/block/goose/discussions/7697) concerns exposing its own Agent runtime. Neither displaced the more specific ccmux/Happier examples. These three were screened at documentation level, not deeply audited.

## Implications for Jarvis

Build the local interface around **observing and addressing ongoing work**. Borrow ccmux's separation of process, terminal and conversation identity; Happier's distinction between tracked sessions and the current action target; and HAPI's compact initial voice context followed by updates. Keep Mux/muxd as the terminal substrate. Structured coding-agent APIs can enrich that interface when they reach the actual runtime owner.

The necessary correctness boundary is an explicit target plus fresh state: machine, process identity, terminal ID, conversation ID where known, and pending request/turn identity. Prefer refusing or deferring a send over changing a human draft, sending into a shell, or approving whichever request happens to appear first. Observation, conversation resumption, runtime takeover, terminal input and semantic steering are separate capabilities and should be advertised separately.

No services were deployed, paid model calls made, or Hari's running coding sessions touched. Audio responsiveness, live approval races, desktop/mobile behavior and Mux compatibility remain untested.

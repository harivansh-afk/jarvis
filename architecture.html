The unit of control is a workload.
A Codex session is one kind of process Jarvis can understand. The same foundation covers a shell, compiler, service or VM.
01 /

What the new model changes

Voice and task reasoning have separate jobs. A slower thought need not block the conversation. Live manages conversational timing and delegation; your application still executes the actions.

02 /

The backend is your choice

Choose the reasoning model, supported effort, instructions and tools. Start with one shared Astra over the five Codex sessions. Their own models and working context stay with them.

03 /

The real work is on Spark

Build reliable identity, observation and control: which workload, which process, which terminal, which turn? GPT-Live does not supply that machine interface.

Where the harness lives — managed delegation vs. your own backend
Recommended starting point

Let OpenAI run the delegation loop.

GPT-Live ⇄ configured Responses model
tool call → Spark → result

OpenAI prepares conversation context and connects the voice frontend to the selected backend. Jarvis defines ordinary functions and executes them locally through the Live sideband.

Model and effort settings can change for subsequent requests. That is configuration control; it is not an automatic difficulty router.

Alternative when routing becomes necessary

Own the delegation loop on Spark.

GPT-Live ⇄ your context + routing service
→ Astra / Hermes / local model

Client delegation lets your service decide which model or harness to consult. You own transcript context, routing, budgets and result delivery.

This is where a small-model / large-model policy belongs. Switching managed and client delegation requires a new Live session.

Design constraints: stopping speech, interrupting a Codex turn and terminating a Linux workload are separate actions. Keep observation local; connect cloud audio intentionally. Astra access through Live and this complete architecture have not been runtime-tested.
